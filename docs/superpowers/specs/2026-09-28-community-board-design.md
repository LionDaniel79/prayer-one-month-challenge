# 56사랑 커뮤니티 게시판 + 좋아요 설계

Base: feature/prayer-one-month-challenge @ 8bf8f2cc2fa72cba14083bc485b671e813a8b1e8.
현재 Next.js/React, 서버 세션, Supabase PostgreSQL prayer_app 비공개 스키마, Vercel 서울 배포를 유지한다. 기도/심방/기도요청/공지/공지 이미지 기능은 보존한다.

## 요구사항
회원 메뉴의 공지 바로 위에 커뮤니티를 추가한다. 관리자 메뉴에도 공지 관리 바로 위에 커뮤니티 관리를 추가한다.
관리자만 폴더 생성/이름 변경/삭제, 게시글 이동 가능. 기본 자유게시판을 제공한다. 삭제는 비어 있는 폴더만, 마지막 폴더는 보존한다.
회원 게시글/댓글 작성과 본인 수정/삭제, 관리자 전체 수정/삭제. 폴더별 목록, 검색, 20개 페이지. 댓글 50개 페이지.
첨부 0~2개, 파일당 6MB(6,291,456 bytes) 이하. 실행 파일/웹 실행 문서는 거부하고 원본 파일명을 경로로 쓰지 않는다.
좋아요는 게시글마다 회원당 하나, 재클릭 취소. 목록/상세 숫자와 본인 상태 표시. liked boolean 원하는 상태를 저장하여 재시도에도 중복/반전 없음. 좋아요 사용자 명단은 노출하지 않는다.

## 구조와 보안
기존 공지 이미지처럼 서버 전용 PostgreSQL bytea를 사용하고 별도 비밀값/공개 버킷을 만들지 않는다. Vercel 요청/응답 4.5MB 한도 내 512KiB 단위 업/다운로드. 브라우저에서 결합 후 다운로드 전 SHA-256 검증.
community_folders/posts/files/file_chunks/comments/post_likes의 6개 추가 테이블. 모든 테이블 RLS, PUBLIC/anon/authenticated 권한 회수.
게시글 FK cascade로 파일/조각/댓글/좋아요 함께 삭제. slot 0/1, 크기 CHECK, likes(post_id,user_id) PK. 이동은 파일을 복제하지 않는다.
모든 API는 서버 세션 확인, 관리 작업 role 확인, 본인/관리자 편집 검사. 초안은 작성자에게만 보임. 게시글/댓글을 HTML로 실행하지 않음. Origin과 읽는 도중 실제 바이트 제한.
발행/파일 변경/좋아요는 같은 게시글 행 잠금 사용. 모든 조각 길이/순서/해시가 맞아야 발행. 응답 유실 재시도는 같은 게시글/댓글 UUID를 사용.
미완료 글은 최대3개, 24시간 만료 후 새 작성 시 정리. 첫 화면에서 본인 미완료 글 확인/삭제, 완전 업로드된 초안 발행 마무리. 실패 시 입력 유지.

## 트레이드오프
파일은 DB 저장량을 사용한다. 큰 규모로 성장하면 비공개 오브젝트 저장소로 이전할 수 있도록 첨부 모듈을 분리한다. 파일에 대한 바이러스 검사는 제공하지 않으므로 신뢰할 수 있는 첨부만 열도록 안내한다.

## 실행/배포
사용자는 중간 확인 없이 전체 구현/배포를 요청했다. 별도 feature/community-board에서 검증하고, 기존 기능 브랜치의 공유 Preview에 통합 배포한다. 과거 main 병합 보류는 그대로 유지하며 배포 종류를 명확히 보고한다.
완료 기준: 전체 단위/lint/build/실제 일회용 DB E2E, 6MB 2파일 바이트 일치, 초과/권한/동시 좋아요/응답유실/삭제 정리/360px 검사, Supabase 추가형 migration 및 보안 점검, 실제 배포 커밋과 접근 확인.
