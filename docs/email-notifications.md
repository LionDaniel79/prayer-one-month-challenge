# 접수 이메일 알림

## 무엇을 보내나요?
관리자가 켠 뒤 정식 서비스에서 새로 정상 접수된 목양지·심방신청·기도요청만 관리자 본인의 Gmail로 한 줄 알림을 보냅니다. 다음은 가상 예시입니다.

```text
1-1샘 김시리가 목양지를 제출하였습니다.
1-1샘 김시리가 11월 1일 오후3시에 심방을 신청했습니다.
1-1샘 김시리가 기도요청을 제출했습니다.
```

샘 소속이 없으면 이름부터 표시합니다. 희망 시간이 `15:00`, `오후 3시 30분`처럼 시간으로만 입력된 경우에만 시각을 넣습니다. `오후 상담 관련 메모` 같은 자유 문장은 복사하지 않고 날짜만 표시합니다. 기도제목·심방 사유·참석자·장소·전화번호·첨부파일은 알림에 넣지 않습니다.

사진/파일 목양지는 업로드 완료와 제출 저장 성공 후에만 알립니다. 심방신청은 기존 Google Calendar 동기화가 정상 완료된 뒤에만 알립니다. 단순 초안, 실패한 요청, 기존 자료, 내용 수정은 새 접수 메일을 만들지 않습니다. 반복 완료 요청은 같은 접수 ID로 중복 생성하지 않습니다.

## 처음 한 번 설정하기 — 관리자

현재 Calendar 연결을 해제하거나 기존 암호화 키를 새로 만들 필요가 없습니다. Google의 메일 발송 승인은 별도로 필요합니다. ChatGPT에 연결된 Gmail은 웹앱의 발송 자격 증명이 아니므로 대신 사용할 수 없습니다.

1. 기존 OAuth Client가 있는 **Google Cloud 프로젝트**를 엽니다.
2. **APIs & Services → Library → Gmail API → Enable**을 누릅니다. 기존 Calendar API는 그대로 둡니다.
3. **Google Auth platform → Data Access → Add or remove scopes**에서 `https://www.googleapis.com/auth/gmail.send`를 추가합니다. 기존 Calendar 범위는 지우지 않습니다. 계정 확인에는 OpenID의 `openid`, `email` 범위를 사용합니다. Gmail 읽기·수정·전체 메일 범위는 필요 없습니다.
4. 기존 Web OAuth Client의 Authorized redirect URIs에 **현재 정식 주소 + `/api/admin/google-calendar/callback`**이 등록되어 있는지 확인합니다. Calendar와 동일한 반환 주소를 쓰되 발송 승인 상태·토큰·쿠키는 구분합니다.
5. 앱에 로그인하고 **관리자 → 대시보드 → 맨 아래 ‘접수 이메일 알림’**을 펼칩니다.
6. **알림 받을 이메일**에 본인의 Gmail 주소를 확인·입력한 뒤 **알림 설정 저장**을 누릅니다. 주소를 바꾸면 기존 알림 연결과 대기 알림은 해제됩니다.
7. **Gmail 연결**을 누르고, 저장한 주소와 **같은 Google 계정**을 선택해 메일 발송을 승인합니다.
8. 돌아온 화면에서 **확인 메일 보내기**를 누릅니다. 받은편지함·스팸함에서 확인합니다. 화면의 ‘발송 접수 완료’는 Gmail API가 접수한 상태이며 받은편지함 도착 자체를 확인한 것은 아닙니다.
9. **접수 이메일 알림 사용**을 체크하고 **알림 설정 저장**을 누릅니다. 이후 새 접수부터 적용됩니다. 과거 접수는 한꺼번에 발송하지 않습니다.

Google 승인 과정은 계정 소유자가 직접 진행해야 합니다. Gmail `gmail.send`는 민감한 권한이며 Google의 동의 화면·앱 검증이 추가로 요구될 수 있습니다. 외부 앱의 Testing 상태에서는 일반적으로 refresh token의 7일 만료 제한이 있으므로 장기 운영 시 게시/검증 상태를 확인합니다. 앱 화면에 새 버튼을 만들거나 배포한 것만으로 Google 승인이 완료되지는 않습니다.

공식 안내: [Gmail 권한](https://developers.google.com/workspace/gmail/api/auth/scopes), [메일 발송](https://developers.google.com/workspace/gmail/api/guides/sending), [Google OAuth](https://developers.google.com/identity/protocols/oauth2).

## 발송과 실패 처리

접수 정보와 최소 알림 데이터를 같은 DB 트랜잭션에서 저장합니다. 서버 응답 뒤 처리하고, 남은 대기 항목은 Supabase의 1분 주기 작업이 다시 확인합니다. 일반적으로 접수 직후 처리되지만 서비스 응답·사용량 제한에 따라 늦어질 수 있습니다.

일시적으로 확실히 거절된 전송이나 발송 전 인증 통신 실패는 제한된 횟수로 재시도합니다. 서버가 중단되거나 네트워크가 끊겨 **Google이 이미 받았는지 모르는 경우**에는 ‘결과 미확정’으로 두고 자동 재발송하지 않습니다. Gmail API와 DB 사이에서 정확히 한 번 전송을 보장한다고 주장하지 않습니다. 미확정 건은 관리자 Gmail에서 수신 여부를 확인합니다.

원래 접수 내용이 수정되어도 새 알림을 보내지 않습니다. 발송 전에 삭제하거나 심방을 취소하면 대기 알림을 취소합니다. 이미 전송을 시작한 메일은 취소 직후에도 도착할 수 있으며, 발송된 메일의 삭제는 Gmail에서 별도로 처리합니다.

**Gmail 알림 연결 해제**는 발송용 로컬 토큰과 대기 알림을 정리하며 기존 Calendar 연결을 직접 수정·삭제·철회하지 않습니다. Google 계정 페이지에서 앱 전체 권한을 철회하면 같은 OAuth Client를 쓰는 Calendar도 영향을 받을 수 있습니다.

## 새 설치 운영자 / 개발자

필수 앱 환경변수 외에 기존 `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `ROSTER_ENCRYPTION_KEY`를 Production에서 사용합니다. 메일 토큰은 명단 키에서 용도가 분리된 키를 유도하여 인증 암호화합니다. 새 SMTP 비밀번호나 Gmail 비밀번호를 채팅·코드에 넣지 않습니다. 이미 저장된 데이터를 위해 기존 키를 보존하세요.

1. 새 설치에는 `drizzle/*.sql` 전체를 순서대로 적용합니다. 기존 설치에는 미적용된 `20261010010000_submission_email_notifications.sql`만 적용합니다. 이미 적용된 마이그레이션을 반복하지 않습니다.
2. 새 설치의 운영자가 SQL Editor에서 본인 소유의 **정식 도메인 원점**을 설정합니다. 주소 끝의 `/`는 제외합니다. 이메일은 위 관리자 화면에서 저장할 수 있습니다.

```sql
update prayer_app.email_notification_settings
set production_origin='https://내프로젝트.vercel.app'
where id=1;
```

3. Supabase SQL Editor에서 `scripts/configure-email-cron.sql`을 실행합니다. 이 스크립트는 `pg_cron`, `pg_net`을 켜고 비밀 토큰을 DB 내부에서 생성해 Vault에 보관합니다. 앱 테이블에는 SHA-256 해시만 보관합니다. 기존 동일 이름의 작업은 갱신합니다. 토큰 원문을 조회·복사하거나 공개 로그에 출력할 필요가 없습니다.
4. Production에 배포한 뒤 위 관리자 연결 절차를 진행합니다. Preview/개발/CI에서는 연결·시험 메일·전송을 거부합니다. DB 트랜잭션의 서버 런타임 표식으로 Preview가 같은 DB를 쓰더라도 접수 알림을 새로 만들지 않습니다. 그래도 개발용 DB는 별도 사용하는 것을 권합니다.

Cron 상태는 Supabase의 **Integrations → Cron**에서 `56love-submission-email`을 확인합니다. `pg_net`의 HTTP 응답은 별도 네트워크 결과를 확인하는 데 사용하며, Cron SQL 성공만으로 메일 도착 성공을 판단하지 않습니다. 작업을 중지하려면 관리자 화면에서 알림을 끄고, 필요하면 해당 Cron 작업만 중지합니다. 다른 기존 작업은 수정하지 않습니다.

## 보관과 개인정보

메일 발송용 테이블·OAuth 상태는 서버 전용이고 브라우저 DB 역할의 읽기/쓰기 권한을 회수했습니다. 액세스 토큰은 메모리에서만 사용하고, refresh token과 PKCE verifier는 암호화합니다. OAuth 상태는 관리자 세션과 묶인 일회용 10분 상태입니다.

Google이 발송을 접수하면 큐의 이름·샘·수신 주소·심방 날짜/시간을 정리합니다. 미완료·실패 데이터도 7일이 지나면 정리하며, 비식별 처리 상태/접수 ID 등 이력은 30일 후 삭제합니다. 정리 주기는 Cron 실행에 의존하므로 작업 중단 시 다시 작동시키거나 관리자에게 삭제를 요청해야 합니다. 발송된 메일과 공급자의 로그/백업 보관은 각 서비스에 따릅니다. 일반 접수 원본·회원 기록을 이 큐 정리가 삭제하는 것은 아닙니다.
